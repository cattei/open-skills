# 配料表判定

## 这个 skill 解决什么

超市里拿起一包零食，背面配料表写着「水、白砂糖、柠檬酸、山梨酸钾、食用香精」——这些到底是什么？哪些要留意？**能不能买？**

这个 skill 把配料表逐项拆开，对着随包知识库逐条匹配，输出一个可以直接给结论的判定：

- **五档购买建议**：推荐购买 / 可以购买 / 适量购买 / 谨慎购买 / 不建议购买
- **逐项安全等级**：安全 / 注意 / 限量 / 禁用，外加两个未收录态
- **每项解释**：它是什么、干什么用、常见误解、特殊人群提示
- **判定依据**：为什么给这个档位，哪些项触发了风险

全程离线纯规则，**不调 LLM、不联网**。同一份输入永远得到同一份结论——这点很重要，因为一个会"发挥"的模型在食品判断上是负债。

## 怎么用

### 最快一步

```bash
python scripts/check.py --text "水、白砂糖、柠檬酸、山梨酸钾、食用香精"
```

输出是给人看的 Markdown。要机读就加 `--json`。

### 参数

| 参数 | 说明 |
|---|---|
| `--text` | 配料表原文（顿号/逗号/分号/换行分隔均可） |
| `--file` | 从 UTF-8 文件读取，长配料表用这个 |
| `--type` | `food`（默认）/ `daily` / `cosmetic`。**必须选对**，见下文「品类隔离」 |
| `--mode` | `general`（默认）/ `child` / `allergy` |
| `--json` | 输出 JSON 而非 Markdown |
| `--kb-report` | 打印知识库统计，排查"为什么没命中" |

### 先确认知识库在不在

```bash
python scripts/check.py --kb-report
```

期望看到食品 376 条、非食品 270 条。如果显示 0，说明 `data/` 缺失，别继续判。

### 自测

```bash
python scripts/selftest.py
```

6 个案例 + 7 条不变量。改完脚本必须跑通再交付。

## 判定规则（与后端一致）

优先级从高到低，命中即返回：

| 条件 | 档位 |
|---|---|
| 含任一 `banned`（禁用）成分 | 不建议购买 |
| `restricted`（限量）≥ 2 项 | 不建议购买 |
| `restricted` = 1 项 | 谨慎购买 |
| 已匹配项中 `caution` 占比 ≥ 40% | 适量购买 |
| `caution` 占比 > 0 但 < 40% | 可以购买 |
| `caution` = 0 | 推荐购买 |

**零命中不是「推荐购买」**——这是本 skill 最重要的一条纪律：

| 情况 | 档位 |
|---|---|
| 食品 + 零命中 + 配料可信（如纯净水、单一原料） | 推荐购买 |
| 食品 + 零命中 + 全是标签噪声（厂名厂址、净含量、单字碎片） | 适量购买 |
| 食品 + 零命中 + 可信项不足半数 | 适量购买 |
| 非食品 + 零命中 | 适量购买 |
| 有任一已匹配项 | 按上表比例规则 |

理由很直白：**没有数据时宣称"安全可放心购买"，等于编造结论。**

### 人群模式

- `child`：命中「婴幼儿不宜」成分时，档位只上调不下调（最低到谨慎购买）
- `allergy`：命中用户预设过敏原则直接不建议购买（需在调用侧传过敏原清单）

## 品类隔离（最容易错的地方）

同一个成分在不同品类下结论**完全不同**。甘油、丙二醇、山梨酸钾在食品和化妆品里都有，但 GB 2760 的食品限量结论**不能**套到化妆品上：

| 品类 | 等级字段 | 依据 |
|---|---|---|
| `food` | `safety_level` | GB 2760 |
| `cosmetic` | `cosmetic_safety_level` | 《化妆品安全技术规范》等 |
| `daily` | `daily_safety_level` | 本品类法规 |

所以 `--type` 必须选对。给化妆品成分表跑 `--type food` 会得到一堆错结论。

## 两个「未收录」态必须区分

这是本模块历史上最容易出 bug 的地方：

| 状态 | 显示 | 含义 |
|---|---|---|
| 知识库真的没有 | **暂未收录** | 我们没这条数据 |
| 已收录、等级待确认 | **已收录 · 等级待确认** | GB 2760 只给"允许品种+类别+限量"，是**合规白名单，不含毒性分级** |

如果把第二态显示成「暂未收录」，287 条 GB 2760 添加剂会被误报成"没收录"，用户会以为知识库残缺；但反过来也不能因为"已收录"就编一个安全等级出来。

## 知识库

随包两份 JSON，是本 skill 的核心资产：

| 文件 | 条数 | 内容 |
|---|---|---|
| `data/knowledge_base.json` | 376 | 食品配料与添加剂，含 GB 2760 依据、限量、常见误解 |
| `data/knowledge_base_nonfood.json` | 270 | 化妆品/日用品成分，含 INCI 别名与本品类法规依据 |

**双轨制真源规则**：这两份文件的真源在这里（`.skills/ingredient-check/data/`）。项目侧 `Project-IngredientAnalyzer/backend/app/data/` 是消费端。**禁止手改消费端**，同步用 `scripts/sync-kb.ps1`（单向 + sha256 校验）。

## 匹配方式

1. **标准名精确** → 2. **别名精确** → 3. **受控模糊**

模糊匹配阈值 0.82，且要求长度比例 ≥ 0.6。收紧是为了避免「植物油」被「氢化植物油」误纳——这类包含型误命中会导致漏掉真正的高风险成分。

英文别名做**大写归一**：库里存 `Aqua`，化妆品标签印 `AQUA`。不做归一的话，整张英文 INCI 成分表命中率是 0。

命中类型为 `fuzzy` 时，输出会标注「疑似：原名 → 标准名」，提醒读者这不是确定命中。

复合配料（`植物油（棕榈油、大豆油）`）会**递归匹配子配料**，子配料同样计入档位统计。

## 边界与明确不做

- **不做** OCR。图片识别归项目侧小程序，本 skill 只处理文本。
- **不做** AI 润色。判定是纯规则，不用 LLM 改写结论。
- **不做**医疗或营养建议。输出只是配料信息的结构化解读。
- **不做**未收录成分的推断。没数据就报没数据。
- 知识库是**人工维护的有限集合**，不是全量 GB 2760 名录；覆盖面以 `--kb-report` 为准，不要假设它无所不包。
