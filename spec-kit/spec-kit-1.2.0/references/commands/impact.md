# 阶段 `impact` — 从用户场景推导说明文档（页面 / 功能 / 数据 / 业务流程）

> 本地新增阶段（非上游 spec-kit）。对应文件：`impact.md`。
> 前置：`stories.md` 已由用户审核；模板：`references/templates/impact-template.md`。
> 这一步只回答"**要动哪里、这个场景怎么走完**"，不回答"用什么技术实现"（那是 `plan`）。

## 目标

把每条用户场景（U#）翻译成四张清单 + 一条端到端业务流程，让后续的验收卡、规格、计划、任务都有落点：

| 问题 | 产出 | 谁接着用 |
|---|---|---|
| 动了哪些页面 | 页面清单（新增/改动/复用 + 入口 + 状态） | 验收卡 ①③、plan 前端部分 |
| 动了哪些功能 | 功能点 F#（现状 vs 目标） | spec 的 FR、plan 的模块 |
| 动了哪些数据 | 数据清单（实体/字段/接口/存储 + 读写 + 兼容） | plan 的数据模型、迁移 |
| 这个场景怎么闭环 | 整体业务流程（步骤 + 分支 + 异常 + 硬规则） | 验收卡 ④、tasks 的顺序 |

## 前置检查

- `stories.md` 存在，且用户已经改过/确认过（先读文件，读不到用户的口头确认就问一句）。
- 还有 `⚠️ 待确认` 的核心项 → 先把问题列给用户，**不要**带着猜测写影响面。

## 执行步骤

1. **读故事**：以 `stories.md` 当前内容为唯一依据（用户改过的优先，不要用你起草时的记忆）。
2. **列 U 清单**：每条 U 一行，写清角色、目标、涉及页面（故事里提到的）。
3. **逐条抽四类影响**：
   - **页面**：新增 / 改动 / 复用；从哪进（入口）、去哪（出口）；关键状态（空/加载/错误/无权限/超限）；共用组件与权限边界。页面用用户叫法（"首页""结果页"），必要时括号注路由。
   - **功能**：功能点编号 `F#`，写"现状 → 目标"；一句话一条，不写实现方式。
   - **数据**：实体 / 字段 / 接口 / 存储；读还是写；变更是新增、改结构还是改语义；要不要兼容旧数据/迁移。
   - **业务流程**：编号步骤走完整个场景；每步写"谁做什么、看到什么"；分支与异常单独列；业务硬规则写死（不满足就禁止操作）。
4. **画流程**：优先编号步骤（谁都看得懂）；有 mermaid 环境可补一张 `flowchart TD`，两者不一致时以编号步骤为准。
5. **建追溯表**：`U# → 流程节点 → 页面 → F# → 数据`，后面验收卡编号出来后补 `RAC` 列。
6. **汇总影响总览**：每条 U 新增/改动页面数、功能数、数据变更数，一眼看出谁最重。
7. **标不确定**：任何一处没把握就写 `[待确认: 具体问题]`，不要用"应该""大概"糊过去。
8. **交人审**：和 story 一样，产出后停下，请用户直接改文件；改完再进 `accept`。

## 硬约束

| 必须 | 禁止 |
|---|---|
| 写"用户要看到/做到什么" | 写技术选型、框架、库、算法（留给 plan） |
| 页面用用户叫法 | 只写路由名/组件名 |
| 数据写"实体 + 读/写 + 变更类型" | 写字段类型、索引、SQL（除非已存在） |
| 每条 U 至少一条端到端流程 | 只画页面关系图，不写业务闭环 |
| 异常/失败路径单列 | 只写正常路径 |
| 不动 `stories.md` | 顺手"优化"用户的用词 |

## 完成标准

- [ ] `impact.md` 存在，每条 U 都有 页面/功能/数据/流程 四节
- [ ] 每条 U 都有端到端流程（含失败/取消路径与硬规则）
- [ ] 追溯表完整，`F#` 编号可直接被 spec 的 FR 引用
- [ ] 影响总览已汇总
- [ ] 不确定项都标了 `[待确认]`，并已列给用户
- [ ] 向用户报告：几条 U / 新增几个页面 / 几条流程 / 待确认几项 / 下一步 `/spec-kit accept`

## 反模式

| 别做 | 为什么 |
|---|---|
| 把 impact 写成技术方案 | 会和 plan 打架，改一处要改两处 |
| 页面清单漏掉空态/错误态 | 验收卡 ① 打不了勾，上线才发现白屏 |
| 数据只写"新增一张表" | plan 无法判断兼容与迁移量 |
| 流程只写"用户操作 → 成功" | 失败路径才是 bug 高发区 |
| 顺手改用户的故事措辞 | 故事是需求源头，措辞是用户的 |
