# 阶段 `accept` — 把故事拆成验收卡（RAC）

> 本地新增阶段（非上游 spec-kit）。对应文件：`acceptance.md`。
> 方法论：`../../references/xp-ai-acceptance.md` §2–§3；模板：`references/templates/acceptance-card-template.md`。

## 目标

把 `stories.md` 的每条故事翻译成 1–N 张**四格验收卡**，让"做完没有"可以逐项打勾，而不是靠感觉。

## 前置

- `stories.md` 存在且用户确认过（没有 → 先跑 `story`）。
- 依赖：每张卡要回链 `U#`；`spec.md` / `tasks.md` 还没生成就标 `TODO`，后面再补。

## 执行步骤

1. **切片**：拿每条故事，找"页面 / 动作"，一个页面或一个动作切一张卡。
   - 粒度：半小时 ~ 半天；
   - > 半天 → 拆；跨多个业务流 → 拆；拆不动 → 回 `story` 重讲。
2. **填四格**（缺一格不许开工）：
   - ① 可见内容：字段/区块/按钮/文案/空态/加载态/错误态/置灰条件；
   - ② 输入：用户输入、数据来源、**边界 / 空 / 异常**三类必须各有条目；
   - ③ 关联：来源页、跳转目标、影响的下游与全局状态、共用组件与权限边界；
   - ④ 业务流：上游→本页→下游、成功路径、失败/取消/退出路径、业务硬规则。
3. **建清单表**：卡号 `RAC-001` 起，列"页面/动作、来源故事、粒度、状态"。
4. **粒度自检**：逐卡问三个问题——能半天做完吗？只覆盖一个页面/动作吗？能单独验收吗？有一个否就拆。
5. **交给人确认**：AI 起草完必须问一句"四格你看有没有漏/多的，特别是②的异常输入和④的失败路径"。
   **人确认之前，不许进入 `implement`。**
6. **写文件**：`acceptance.md`（模板见 `references/templates/acceptance-card-template.md`）。

## 与故事、规格的追溯

```
U1 ──┬── RAC-001（首页拍照入口）
     ├── RAC-002（分析页结论区）
     └── RAC-003（配料逐项解释表）
spec.md 的 FR-003 ←→ RAC-002
tasks.md 的 T007  ←→ RAC-002
```

- 每条故事至少 1 张卡；每张卡必须能指回一个 `U#`。
- `spec.md` 生成后，把每张卡的「关联规格」填上 FR 编号；`tasks.md` 生成后补 T 编号。
- **卡和故事冲突时以故事为准**：改卡或改故事，并记录在 `stories.md` 的变更记录里。

## 完成标准

- [ ] `acceptance.md` 存在，卡清单表完整（卡号/页面/来源故事/粒度/状态）
- [ ] 每张卡四格填满，②含边界/空/异常，④含失败路径与硬规则
- [ ] 每张卡粒度 ≤ 半天，且能单独验收
- [ ] 用户已确认（或在文件里标出未确认的卡）
- [ ] 向用户报告：几张卡 / 哪几张未确认 / 下一步 `/spec-kit specify`（或直接 `plan`）

## 反模式

| 别做 | 为什么 |
|---|---|
| 让 AI 自己定四格然后自己验收 | 它永远判"通过" |
| "① 页面正常显示"这种空话 | 无法打勾，等于没写 |
| 一张卡塞三个页面 | 验收时说不清哪条没过 |
| ② 只写正常输入 | 异常输入才是 bug 高发区 |
| ④ 不写失败/取消路径 | 线上问题八成出在这 |
