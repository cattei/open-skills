# 阶段 `verify` — 按验收卡验收，把结果回填到故事

> 本地新增阶段（非上游 spec-kit）。产出：更新 `acceptance.md` 的验收记录 + `stories.md` 的实现核对。
> 这是"**用户故事即验收结果**"落地的那一步。

## 目标

实现完之后，逐格验收，最后得到两份东西：
1. `acceptance.md`：每张卡的 `✅ 全过 / ⚠️ 部分 / ❌ 未过` + 差距描述；
2. `stories.md`：每条故事的「实现核对」表逐条打勾 + 缺口编号 `G#` + 能力清单状态。

## 前置

- `acceptance.md` 存在且用户确认过；代码已实现（或部分实现）。
- **跑得起来**：能给页面/接口的入口（本地地址、截图、测试命令）。跑不起来就别验收，先说清缺什么。

## 执行步骤

1. **准备证据**：把要验收的服务跑起来；能截图就截图，能取日志就取日志。**没有证据不算验过。**
2. **逐卡走四格**（顺序不能跳）：
   - ① 打开页面逐项看：有没有、文案对不对、状态（空/加载/错误/置灰）对不对；
   - ② 喂四类输入：正常 → 边界 → 空 → 异常；
   - ③ 点跳转、看联动、看全局状态有没有串；
   - ④ 从头走业务流，含失败 / 取消 / 中途退出。
3. **打勾规则**：AI 可以逐条报告"我看到什么"，但**结果由人确认**。AI 不得单方面判定"全过"；用户不在场时，状态写 `⏳ 待人工确认`。
4. **有差距就精确回写**（格式固定，不要写"不对，再改改"）：

   ```text
   RAC-002 未通过
   - ①-3：没有"是否建议购买"结论块，只有一张表（期望：结论置顶）
   - ②-5：断网白屏，无提示（期望：提示"网络异常，重试"）
   - ④-2：返回后首页品类选择被重置（期望：保留上次选择）
   ```

5. **全绿才回填**：`stories.md` 对应故事的「实现核对」逐条 `✅`，页面上确实没做的写 `⚠️` 并登记 `G#`。
6. **提交提示**：提醒用户小步提交，提交信息带卡号（`feat: RAC-002 分析页结论置顶`）。
7. **闭环外环节**：一个业务流全绿 → 建议内部发版 → 真实用 5 分钟 → 新问题变成新卡（回到 `accept`）。

## 结果口径

| 结论 | 含义 | 下一步 |
|---|---|---|
| `✅ verified` | 四格全过，故事核对表全 ✅ | 归档卡片，进下一张/下一故事 |
| `⚠️ partial` | 主路径通，异常/边缘未过 | 回 `implement` 修，或改卡（人决定） |
| `❌ failed` | 主路径都不通 | 回 `implement`，不要"先上线再说" |
| `⏳ 待人工确认` | AI 无法自证（需真机/需账号/需人眼判断） | 明确列出要人做什么 |

## 完成标准

- [ ] 每张卡都有验收记录（人/日期/结果/差距）
- [ ] `stories.md` 的「实现核对」已回填，缺口都有 `G#` 编号与处置
- [ ] 能力清单状态同步
- [ ] 向用户报告：全过几张 / 有差距几张 / 差距清单 / 下一步（`converge` 或 `implement`）

## 禁止

- ❌ 没跑起来就说"应该没问题"
- ❌ 只验正常路径
- ❌ AI 自己把 `☐` 改成 `☑`
- ❌ 发现差距却只口头说、不写进卡片
- ❌ 用"差不多""基本可用"结案
