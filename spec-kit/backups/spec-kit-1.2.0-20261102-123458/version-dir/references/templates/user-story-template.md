# 用户故事 — <项目名 / 模块名>

> **状态**：草稿 / 已与用户确认 / 已实现核对（验收后改这一行）
> **用途**：既是**需求源头**，也是**验收结果**。
> - 需求方向：`spec.md` 的每条 FR、每个页面、每句文案，都要能追溯回这里的 U 编号；
> - 验收方向：实现完在每条故事的「实现核对」里逐条打勾，故事与代码不一致时**以故事为准**（或先把故事改清楚再改代码）。
> **写法**：用户对着页面口述，AI 原话记录 + 追问澄清，**不要**把用户的日常话改写成需求术语。

---

## 0. 怎么用（讲 → 记 → 用）

| 步骤 | 谁做 | 做什么 |
|---|---|---|
| ① 讲 | 用户 | 假装第一次用这个产品，从"我在哪、想干什么"讲到"最后看到什么"。讲到页面元素时用眼睛看到的东西描述（"一个很大的按钮"），不要用组件名 |
| ② 追问 | AI | 每条故事补齐 4 件事：**入口**（从哪来）、**输入**（点了/填了/拍了什么）、**看到**（逐项，含文案与状态）、**万一**（失败/没网/没权限/输错会怎样） |
| ③ 复述 | AI | 用一段话复述给用户确认："你的意思是……对吗？" 有歧义就停在待确认，不猜 |
| ④ 拆卡 | AI | 每条故事拆成 1–N 张验收卡（见 `acceptance.md`），卡里回链 U 编号 |
| ⑤ 验收 | 用户 + AI | 实现后按卡片验收，把结果回填到本文件「实现核对」+ `acceptance.md`「验收记录」 |

**硬规矩**

- 一条故事 = 一个用户 + 一个目标 + 一个页面闭环；跨页面的拆成多条。
- 故事里**不出现**接口名、字段名、框架、类名；出现即改写。
- 只写真发生过或真会发生的场景，不编造用户画像。
- 一个故事里最多 3 个"待确认"，多了说明故事还没想清楚。
