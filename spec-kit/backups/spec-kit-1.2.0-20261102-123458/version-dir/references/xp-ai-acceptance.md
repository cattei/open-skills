# AI + XP：结果验收与用户故事（本 skill 的验收底座）

> 来源：`0项目集规划/XP实践/AI+XP协同开发最佳实践指南.md`（v1.0，孙永乐）+ `Project-IngredientAnalyzer/规划/用户故事-买菜帮手.md`（实例）。
> 本文件是**自包含摘要**：在别的仓库/别的机器上，没有那两份原文也能按这里做。

## 1. 为什么把 TDD 换成结果验收

| 假设 | 现实 |
|---|---|
| AI 会忘了写测试 | 不会，它会写出 100% 通过的单测——但测的可能不是业务要的 |
| 单测通过 = 功能对 | 不等价。用户视角的问题是"这个页面能不能把这件事做完" |
| 人的价值在写代码 | 人的最高杠杆是**定义"什么叫做完"**，然后审 AI 的交付 |

结论：**反馈粒度从代码级红绿，变成页面级、业务级是否符合预期。**

## 2. 验收卡（RAC）：四格必填

```
① 可见内容：页面上必须看到什么（字段/文案/按钮/状态/提示；何时显示/隐藏/置灰/报错）
② 输入：内容从哪来、用户喂什么（填/点/传参/接口/表/上一页；边界/空/异常分别怎样）
③ 关联：和哪些页面/动作有关（从哪跳进、跳回哪、影响哪些下游/全局状态、组件权限边界）
④ 业务流：在哪个闭环里（上下游、成功路径、失败/取消/中途退出、业务硬规则）
```

四格之外还要有 **验收记录**：验收人 / 日期 / 结果 ☑全过 ☐有差距 / 差距描述（哪格、哪条、实际看到什么）。

### 验收动作（顺序不能跳）

1. **人写卡片**（AI 可以起草，人必须确认）——不让 AI 自己定验收标准，也不让它自己打勾；
2. 卡片喂给 AI → 实现；
3. 不先读代码，直接：①打开页面逐项看 → ②喂正常/边界/空/异常输入 → ③点跳转看联动 → ④从头走业务流；
4. 不对 → 精确回写"哪一格 / 哪一条 / 实际看到什么"，不要说"不对再改改"；
5. 全绿 → 归档，提交信息带卡片号（`feat: RAC-012 订单详情页可取消`）。

> 铁律：**验收不通过时回到卡片，不是回到代码。** 先判断是卡片漏写，还是实现错了。

## 3. 粒度与节奏

- 一张卡 = 一个页面/一个动作，**半小时 ~ 半天**；超过半天 → 拆；跨多个业务流 → 拆；拆不动 = 需求没想清楚。
- 一张卡一个会话/一个上下文窗口；卡片做完开新会话，避免长上下文导致漂移。
- 每 2–3 张卡做一次"只重构不改行为"，重构后重跑受影响卡片的业务流。
- 一个业务流闭环 → 内部发版 → 自己真实用 5 分钟 → 问题变成新卡片（不记在脑子里）。

## 4. 反模式

| 反模式 | 正确做法 |
|---|---|
| 让 AI 写验收标准、自己验收自己 | 标准人写，四格填全 |
| 一个超长会话做完整功能 | 一卡一会话 |
| 不固化项目规范，每次重复解释 | 项目根放 `AI_RULES.md`（技术栈/目录/固定写法/禁止事项），新会话先读 |
| AI 写完直接通读代码 | 按卡片跑页面、跑业务流 |
| 攒一周代码一次提交 | 一卡一提交，提交信息带卡号 |
| 接受"看起来差不多" | 哪条没打勾就回去改 |
| 让 AI"顺便把未来可能用得上的也写了" | 显式禁止，只做当前卡片 |
| 验收只点正常路径 | ②格必须列异常输入 |
| 疲劳时继续验收 | 停，明天再看——疲劳会降低验收标准 |

## 5. 与用户故事的关系（本 skill 的扩展）

XP 指南只说"每次功能先写验收卡"。本 skill 往前补一层：**用户故事**。

```
用户故事（用户对着页面口述）→ 验收卡（四格）→ spec（FR 回链 U 编号）→ plan → tasks
      ↑                                                            ↓
      └────────── 验收结果回填（实现核对 + RAC 打勾）←── implement/verify
```

- 故事是**需求来源**：一切 FR、页面、文案都要能追溯到某个 U 编号；
- 故事也是**验收结果**：实现完在故事上逐条填"实现核对"，不一致时以故事为准（或先改故事再改代码）。
- 验收卡是两者之间的桥：故事说"用户看到什么"，卡片说"我按什么逐项打勾"。
