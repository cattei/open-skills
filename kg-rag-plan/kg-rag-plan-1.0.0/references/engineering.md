# 六项关键工程设计（KG-RAG 与 Naive RAG 的分水岭）

> 这六项是绝大多数 KG-RAG 项目翻车的地方。方案里必须逐项写明做法，不能只写"要做实体消歧"。

## 1. 实体消歧（头号难题）

**问题**：同义实体未合并（"华为" / "华为技术有限公司" / "HUAWEI"），导致图谱碎片化、多跳路径断裂。图谱越大越严重。

**对策**：建立独立的实体消歧管线，**而非仅靠 Prompt 调优**。

```
入图前流程：
原始实体 → 字典精确匹配 → 命中则替换为规范名
         → 未命中 → LLM 语义合并判断 → 合并/新建
         → 写入规范实体字典
```

- **规范实体字典**：从企业主数据 / CRM / 产品目录导入，作为消歧基准
- **LLM 兜底合并**：字典未命中的实体，用 LLM 判断是否与已有实体同义
- **质检目标**：实体重复率 **< 8%**（原方案 15% 过松）
- **实施阶段**：阶段 1.4 小批量试建图时即引入，阶段 1.5 质检验证

**为什么不能只调 Prompt**：Prompt 只能影响单次抽取，管不住跨文档、跨批次的实体一致性。字典才是基准。

## 2. 图谱生命周期管理（增/改/删）

**问题**：只做增量入图（新增），不覆盖文档更新和删除。直接追加会导致新旧实体矛盾，级联删除可能误删共享实体。

**对策**：建立文档→图谱的溯源映射，三种操作分别处理：

| 操作 | 策略 | 说明 |
|---|---|---|
| 新增文档 | 直接入图 | LightRAG 增量 insert，成本极低 |
| 更新文档 | **删旧子图 → 重新抽取入图** | 非追加，避免新旧实体矛盾 |
| 删除文档 | 删该文档**独占**实体，共享实体保留并标记"来源减少" | 防止级联删除误伤 |

- **溯源映射**：维护 `document_id → [node_ids, edge_ids]` 映射表
- **共享实体判定**：实体被 ≥ 2 个文档引用即为共享，删除时不清理
- **实施阶段**：阶段 2.6 增量管道必须覆盖增/改/删三种场景

**更新为什么必须"删了重抽"**：追加会让新旧版本的同一实体产生矛盾属性（旧价格 vs 新价格），图谱里两个都留着，检索时随机命中一个。

## 3. 图级权限穿透防护

**问题**：知识图谱的 traversal 天然穿透权限边界。用户 A 无权看文档 X，但多跳检索可能经过文档 X 抽取的实体作为中间跳板，答案间接泄露信息。

**示例**：A 能查"项目 P 的负责人"，B 能查"某人的汇报线"，A 问"项目 P 负责人的上级是谁"——两跳就绕过了权限。

**对策**：双层防护：

1. **检索层**：对召回的每条图谱路径，校验路径上**所有实体**的来源文档权限，无权路径直接剪枝
2. **生成层**：Prompt 中注入用户权限范围，LLM 生成时自动规避越权内容

- **测试要求**：阶段 2.5 权限测试必须包含**跨权限多跳攻击用例**
- **对抗用例示例**：低权限用户故意问高密级内容，验证拒答或脱敏

**只做一层不够**：只做检索层剪枝，LLM 仍可能从上下文推断；只做生成层，越权内容已经进了 Prompt。

## 4. 分级检索路由

**问题**：Mix 模式（图谱+向量全跑）延迟最高，但常被设为默认。约 40% 的问题是简单事实型，无需走完整图谱链路。

**对策**：分级路由 + Query 理解前置：

```
用户提问
  ↓
Query 理解（意图识别 + 实体标注 + Query 改写 + 多轮上下文解析）
  ↓
路由决策：
  简单事实型 → Local（实体邻域，最快）        ← 默认
  关系推理型 → Mix（图谱+向量双路）
  全局归纳型 → Global（社区摘要）
  ↓
置信度低 → 自动升级到 Mix
```

- **Query 理解层**（新增）：路由前必须先做意图识别、实体标注、口语化改写、多轮指代消解
- **默认 Local 而非 Mix**：预计平均延迟降 40-60%，P95 从 8s 降到 3-5s
- **流式输出**：图谱链路延迟高，必须流式缓解体感
- **语义缓存**：高频相似问题命中缓存直接返回
- **API 并发优化**：Embedding/Rerank/LLM 均走线上 API，注意并发限流；批量 Embedding 请求合并发送
- **实施阶段**：阶段 2.3 检索模式配置时实现

## 5. 模型 API 成本控制

**问题**：全量建图 LLM 调用量巨大（经验值：每 100 万字文档消耗数百万 token），Embedding/Rerank/LLM 全走线上 API，成本需精确管控。

**对策**：

- **阶段 2.1 先小批量实测**：取 100 份文档实测各 API 单耗（LLM/Embedding/Rerank 分别计量），外推全量成本，确认预算后再放全量
- **启用 LightRAG 缓存**：重复实体/关系抽取命中缓存，跳过 LLM API 调用
- **分批入库**：每批 500 份，失败自动重试，断点续传
- **API 限流配置**：建图阶段并发量大，配置各 provider 的 QPS 限流，避免触发限流或欠费
- **抽取模型红线**：测试阶段可降级模型，**最终建图不得使用弱模型**
- **Embedding 批量化**：批量请求合并发送，减少调用次数和网络开销

**成本外推公式**（经验值，需实测校准）：

```
建图 token ≈ 文档总字数 / 100万 × 200万~500万
建图成本   ≈ 建图 token / 1000 × 模型单价(¥/千token)
```

## 6. LightRAG 生产成熟度应对

**问题**：LightRAG 是学术开源项目，非商业产品，存在 API breaking change、大规模稳定性未充分验证等风险。

**对策**：

- **版本锁定**：锁定具体 commit/tag，**fork 一份做内部维护**，不直接 `pip install` 跟最新
- **阶段 0.7 压测**：环境就绪后先用 10 万字文档压测，验证内存泄漏和并发稳定性
- **监控告警**：Langfuse 监控 LightRAG 内部异常率，超阈值告警

## 风险矩阵

| 风险 | 等级 | 对策 | 对应章节 |
|---|---|---|---|
| 建图 API 成本超预期 | 中 | 阶段 2.1 先实测各 API 单耗再放全量；启用缓存；抽取模型不得降级；配置限流 | §5 |
| 图谱抽取质量差 | 高 | 抽取必须用 DeepSeek-V3/Qwen-Max 级别；质检不过调 Prompt 重抽 | §1 |
| 实体消歧不充分 | 高 | 字典匹配 + LLM 兜底合并，重复率 < 8% | §1 |
| 文档更新导致图谱腐化 | 高 | 增/改/删全覆盖管道 + 溯源映射 + 共享实体保护 | §2 |
| 权限穿透泄漏 | 高 | 检索层路径权限校验 + 生成层权限注入 + 对抗测试 | §3 |
| 多跳链路延迟高 | 中 | 默认 Local 路由 + 流式输出 + 语义缓存 + Query 理解分流 | §4 |
| LightRAG 生产稳定性 | 中 | 版本锁定 + fork 维护 + 阶段 0 压测 + 监控告警 | §6 |
| 幻觉引发业务事故 | 高 | 拒答红线 + 强制引用 + 影子期专查 P0 + 随时回退 | 阶段 3.3 / 4 |

## 技术栈与存储

| 层 | 组件 | 版本建议 |
|---|---|---|
| 核心引擎 | LightRAG（HKUDS） | 锁定 tag，fork 内部维护 |
| 图存储 | Neo4j Community | 5.x |
| 向量存储 | Milvus | 2.4+ |
| KV/文档 | PostgreSQL | 16+ |
| 文档解析 | MinerU | 2.x |
| OCR 兜底 | PaddleOCR | 4.x |
| Embedding | 线上 API（硅基流动/智谱/OpenAI） | — |
| Rerank | 线上 API（硅基流动/Cohere） | — |
| 评估 | RAGAS | 0.2+ |
| 可观测 | Langfuse（自托管） | 3.x |
| 部署 | Docker Compose | — |

**存储演进**：数据量 < 50 万 chunk 时用 PostgreSQL 三合一（pgvector + AGE），跑通后再拆。

| 指标 | 阈值 | 动作 |
|---|---|---|
| 向量数 | > 200 万 | 拆出 Milvus 独立容器 |
| 图节点数 | > 100 万 | 拆出 Neo4j 独立容器 |
| 并发 QPS | > 50 | 应用层水平扩展 + 读写分离 |
